PREMORTEM · Arquitectura de datos para Supabase

PREMORTEM: capa de datos

Una sola fuente de verdad, escrituras por funciones SQL, lecturas por RLS y cifrado de sobre para lo confidencial.

Versión 1.0 Fecha 03/10/2026 Clasificación Información Organizacional Estado Propuesta de diseño

La recomendación: Postgres de Supabase como única fuente de verdad, con el simulador escribiendo solo a través de funciones SQL transaccionales, el navegador leyendo solo con RLS, una cola pgmq para los trabajos, Realtime como señal de refresco y cifrado de sobre en la aplicación para los pocos campos que de verdad son confidenciales.

Documento superado (03/10/2026). Esta propuesta fue auditada y reemplazada por docs/PREMORTEM_SPEC_V2.md. El esquema vigente está en supabase/migrations/ (jobs por mundo, efectos genéricos, roles de conexión sin DML, evidencia con formato versionado y billing). Se conserva como antecedente de diseño.

Tres principios que ordenan todo

Integridad

La evidencia no se edita. Claves foráneas compuestas, restricciones únicas, tablas append-only y una cadena de hashes hacen que una traza alterada sea detectable y que un ID de otro mundo no pueda colarse.

Velocidad

Cada llamada de herramienta es una transacción corta en una función SQL, con dos bloqueos de fila y dos índices. El estado del mundo cabe en un JSONB pequeño. Realtime solo avisa; la base responde.

Confidencialidad

Clasificar antes de cifrar. Se cifran los prompts y el texto generado por el modelo, no los IDs ni los importes del simulador. Así RLS, índices y auditoría siguen funcionando.

Mapa de entidades

Doce tablas en dos esquemas. public es lo que el navegador puede leer con RLS. core no se expone a la API de Supabase: ahí viven los oráculos, las claves y las funciones del simulador.

Qué se cifra y qué no

Supabase ya cifra los discos en reposo y el tráfico va por TLS. El cifrado por columna se reserva para lo que un administrador de la base no debería poder leer en claro.

Cómo funciona el cifrado de sobre

Se descartó el cifrado dentro de Postgres con pgcrypto porque la clave viajaría dentro de la sentencia SQL y puede acabar en los logs. El cifrado ocurre en el servidor de aplicación, con AES-256-GCM, antes de tocar la base.

1

Una DEK por propietario

Al primer dato confidencial de un usuario se genera una clave de 32 bytes. Se guarda envuelta con la KEK en core.data_keys.

2

La KEK fuera de la tabla

Vive en Supabase Vault o en la variable de entorno de los procesos de servidor. Se lee al arrancar y se cachea en memoria.

3

Cifrar con contexto

El dato se cifra con la DEK y un nonce aleatorio. Los datos adicionales autenticados atan el texto cifrado a su tabla, fila y propietario.

4

Descifrar con registro

Solo la API y el worker descifran. Cada lectura de un prompt o export deja una fila en core.access_log.

Formato del blob y datos autenticados

bytea = 0x01 ‖ key_id (16 bytes) ‖ nonce (12 bytes) ‖ ciphertext ‖ tag GCM (16 bytes)

AAD (no se guarda, se recalcula):
  "premortem:" ‖ tabla ‖ ":" ‖ columna ‖ ":" ‖ id_fila ‖ ":" ‖ owner_id
  para events, que no conocen su id antes de insertar:
  "premortem:events:payload:" ‖ attempt_id ‖ ":" ‖ owner_id

El byte de versión permite cambiar el formato sin migrar. El key_id dentro del blob permite rotar la DEK sin reescribir las filas antiguas. Los datos autenticados impiden que un texto cifrado se copie de una fila a otra o de un usuario a otro: el descifrado falla.

// src/server/crypto.ts (Node, sin dependencias externas)
import { createCipheriv, createDecipheriv, randomBytes } from "node:crypto";

export function seal(dek: Buffer, keyId: Buffer, aad: string, plain: string): Buffer {
  const nonce = randomBytes(12);
  const c = createCipheriv("aes-256-gcm", dek, nonce);
  c.setAAD(Buffer.from(aad));
  const ct = Buffer.concat([c.update(plain, "utf8"), c.final()]);
  return Buffer.concat([Buffer.from([1]), keyId, nonce, ct, c.getAuthTag()]);
}

export function open(resolveDek: (keyId: Buffer) => Buffer, aad: string, blob: Buffer): string {
  if (blob[0] !== 1) throw new Error("ENC_VERSION");
  const keyId = blob.subarray(1, 17), nonce = blob.subarray(17, 29);
  const tag = blob.subarray(blob.length - 16), ct = blob.subarray(29, blob.length - 16);
  const d = createDecipheriv("aes-256-gcm", resolveDek(keyId), nonce);
  d.setAAD(Buffer.from(aad)); d.setAuthTag(tag);
  return Buffer.concat([d.update(ct), d.final()]).toString("utf8");
}

Dónde vive la KEK

OpciónCuándoVentajaCoste

KMS de nube (AWS, GCP)Producción con clientes externosLa KEK nunca sale del HSM; auditoría nativaLatencia en el envoltorio, un proveedor más

Recomendación: empezar con variable de entorno, dejar kek_id en cada fila de data_keys desde el día uno, y mover la KEK a Vault o KMS sin tocar datos. Rotar la KEK solo re-envuelve las DEK. Rotar una DEK crea una clave activa nueva; las filas antiguas siguen descifrándose por su key_id.

Escritura: funciones SQL y bloqueos

supabase-js no hace transacciones de varias sentencias. Por eso cada herramienta del simulador es una función en core, llamada por el worker con una conexión directa y un rol propio.

-- Rol del worker: mínimo privilegio, nunca service_role ni postgres
create role premortem_worker login noinherit;         -- contraseña fuera de Git
grant usage on schema core, public to premortem_worker;
grant execute on all functions in schema core to premortem_worker;
grant select, insert, update on public.runs, public.worlds, public.world_attempts to premortem_worker;
grant select, insert on public.events, public.refunds, public.findings to premortem_worker;
grant select on core.task_oracles, core.data_keys to premortem_worker;
grant insert on core.access_log to premortem_worker;
revoke all on all functions in schema core from anon, authenticated;
-- core.sim_create_refund: una llamada de herramienta = una transacción
create or replace function core.sim_create_refund(
  p_run_id uuid, p_attempt_id uuid, p_lease_token uuid,
  p_order_id text, p_amount_cents bigint, p_currency char(3), p_operation_key text
) returns jsonb
language plpgsql security definer set search_path = core, public, pg_temp as $$
declare
  v_run  public.runs%rowtype;
  v_att  public.world_attempts%rowtype;
  v_prev public.refunds%rowtype;
  v_fp   bytea := digest(p_order_id || '|' || p_amount_cents || '|' || p_currency, 'sha256');
  v_seq  int; v_hash bytea; v_prevhash bytea; v_refund_id uuid; v_drop boolean;
begin
  -- 1. bloqueo run → intento; lease vigente; run e intento activos
  select * into v_run from public.runs where id = p_run_id for update;
  if v_run.status <> 'running' or v_run.lease_token is distinct from p_lease_token
     or v_run.lease_until < now() then
    raise exception 'LEASE_INVALID' using errcode = 'P0001';
  end if;
  select * into v_att from public.world_attempts
   where id = p_attempt_id and status = 'running' for update;
  if not found then raise exception 'ATTEMPT_NOT_ACTIVE'; end if;

  -- 2. idempotencia: misma clave + mismos argumentos = mismo recibo, sin efecto
  select * into v_prev from public.refunds
   where attempt_id = p_attempt_id and operation_key = p_operation_key;
  if found then
    if v_prev.fingerprint = v_fp then
      return jsonb_build_object('ok', true, 'replayed', true, 'receipt_id', v_prev.id);
    end if;
    return jsonb_build_object('ok', false, 'code', 'IDEMPOTENCY_CONFLICT', 'effect_status', 'none');
  end if;

  -- 3. mutaciones pendientes (p. ej. revocar permiso), permiso y saldo, todo sobre v_att.state
  --    ... devuelve FORBIDDEN / AMOUNT_EXCEEDS_REMAINING con effect_status 'none' si procede

  -- 4. evento + ledger + estado, atómicos
  update public.world_attempts set next_seq = next_seq + 1
   where id = p_attempt_id returning next_seq into v_seq;
  select event_hash into v_prevhash from public.events
   where attempt_id = p_attempt_id and seq = v_seq - 1;
  v_hash := digest(coalesce(v_prevhash, '\x'::bytea) || convert_to(p_attempt_id::text || v_seq, 'utf8')
                   || convert_to(p_order_id || p_amount_cents || p_currency || p_operation_key, 'utf8'), 'sha256');
  insert into public.events (attempt_id, world_id, owner_id, seq, type, visible_to_agent, payload, prev_hash, event_hash)
  values (p_attempt_id, v_att.world_id, v_att.owner_id, v_seq, 'tool.create_refund', true,
          jsonb_build_object('order_id', p_order_id, 'amount_cents', p_amount_cents, 'currency', p_currency,
                             'operation_key', p_operation_key), v_prevhash, v_hash);
  insert into public.refunds (attempt_id, world_id, owner_id, request_id, order_id, customer_id, operation_key,
          fingerprint, amount_cents, currency, permission_at_commit, event_seq)
  values (p_attempt_id, v_att.world_id, v_att.owner_id, v_att.state->>'request_id', p_order_id,
          v_att.state#>>array['orders', p_order_id, 'customer_id'], p_operation_key, v_fp,
          p_amount_cents, p_currency, true, v_seq)
  returning id into v_refund_id;
  update public.world_attempts
     set state = jsonb_set(state, array['orders', p_order_id, 'refunded_amount_cents'],
                 to_jsonb((state#>>array['orders', p_order_id, 'refunded_amount_cents'])::bigint + p_amount_cents))
   where id = p_attempt_id;

  -- 5. la pérdida de respuesta se decide aquí pero se aplica en el gateway Node, después del commit
  v_drop := (v_att.state->'pending_mutations' ? 'commit_ack_lost');
  return jsonb_build_object('ok', true, 'receipt_id', v_refund_id, 'seq', v_seq, 'drop_response', v_drop);
end $$;

La función devuelve drop_response y el gateway en Node es quien le enseña TIMEOUT_UNKNOWN al agente. El reembolso ya está confirmado. Así se modela exactamente el fallo posterior al commit sin romper la transacción.

Append-only y cadena de hashes

create or replace function core.forbid_change() returns trigger language plpgsql as $$
begin
  if tg_op = 'UPDATE' and current_setting('premortem.retention', true) = 'on'
     and new is not distinct from (old #= hstore('payload_enc', null)) then
    return new;                      -- única edición permitida: borrar texto cifrado por retención
  end if;
  raise exception 'IMMUTABLE_%', tg_table_name;
end $$;
create trigger events_immutable  before update or delete on public.events   for each row execute function core.forbid_change();
create trigger refunds_immutable before update or delete on public.refunds  for each row execute function core.forbid_change();
create trigger findings_immutable before update or delete on public.findings for each row execute function core.forbid_change();

Cada evento guarda el hash del anterior. Al exportar, la API recalcula la cadena y la incluye en el bundle. Quien reciba el export puede verificar que ningún evento fue insertado, borrado o alterado. En Postgres, el texto de un jsonb es canónico (claves ordenadas), así que hashear payload::text es determinista.

Cola de trabajos en la misma transacción

-- core.create_run: valida, inserta run + mundos + intentos y encola, todo o nada
perform pgmq.send('premortem_jobs', jsonb_build_object('run_id', v_run_id));

-- worker: reclamar con 60 s de visibilidad, renovar mientras trabaja, archivar al terminar
select msg_id, message->>'run_id' from pgmq.read('premortem_jobs', 60, 1);
select pgmq.set_vt('premortem_jobs', :msg_id, 60);
select pgmq.archive('premortem_jobs', :msg_id);

Si pgmq no estuviera disponible en el entorno local, una tabla jobs leída con for update skip locked da la misma garantía. El contrato del worker no cambia.

Lectura: RLS, esquemas y Realtime

-- Patrón único para todas las tablas de public
alter table public.events enable row level security;
create policy events_owner_select on public.events
  for select to authenticated using (owner_id = (select auth.uid()));
-- sin políticas de insert/update/delete para authenticated: el navegador no escribe
create policy events_worker_all on public.events
  to premortem_worker using (true) with check (true);
create index events_owner_idx on public.events (owner_id);
  • owner_id en todas las tablas. Evita subconsultas en cada política y hace que Realtime y los índices trabajen sobre una columna local.
  • (select auth.uid()) entre paréntesis. Postgres lo evalúa una vez por sentencia, no por fila.
  • Esquemas expuestos a la API: solo public. core queda fuera de PostgREST por configuración, además de por permisos.
  • El navegador lee con su sesión; las mutaciones de control (crear run, cancelar, reducir) pasan por la API de Next.js, que valida la sesión y llama a core.*.

Realtime como señal, no como transporte

-- Trigger en events: avisa por canal privado del run con un payload mínimo
create or replace function core.notify_event() returns trigger
language plpgsql security definer set search_path = '' as $$
declare v_run uuid;
begin
  select run_id into v_run from public.worlds where id = new.world_id;
  perform realtime.send(
    jsonb_build_object('attempt_id', new.attempt_id, 'seq', new.seq, 'type', new.type),
    'event', 'run:' || v_run::text, true);
  return null;
end $$;
create trigger events_notify after insert on public.events for each row execute function core.notify_event();

-- Solo el dueño puede suscribirse a run:{id}
create policy run_topic_owner on realtime.messages for select to authenticated
  using (exists (select 1 from public.runs r
                 where 'run:' || r.id::text = realtime.topic() and r.owner_id = (select auth.uid())));

La interfaz recibe el aviso y pide a la API los eventos posteriores a su último seq. Si Realtime se cae, hace sondeo cada pocos segundos. La base siempre es la fuente de verdad y nunca viaja texto cifrado por el canal.

Casos de datos reales

Qué ocurre en la base en las situaciones que la demo y la operación van a provocar de verdad.

1. Dos POST /api/runs con la misma Idempotency-Key

integridad

El cliente reintenta por un timeout de red. Ambas peticiones llegan casi a la vez.

-- request_hash = digest(body::jsonb::text, 'sha256')  → el orden de claves no importa
insert into public.runs (owner_id, idempotency_key, request_hash, ...) values (...)
on conflict (owner_id, idempotency_key) do nothing returning id;
-- si no devuelve id: leer el existente; si su request_hash difiere → 409 IDEMPOTENCY_CONFLICT
Resultado en la baseUn run, cuatro mundos, cuatro intentos y un mensaje en la cola. La segunda petición recibe el mismo run_id con 202.

2. Respuesta perdida: 25 USD se convierten en 50

violación

El agente ingenuo reintenta con otra clave. Así queda la evidencia del intento:

Por qué se sostieneEl evento 5 no es visible para el agente pero sí para el inspector. El validador suma el ledger por request_id, no por clave. Los dos recibos apuntan a sus eventos por FK.

3. Reintento correcto con la misma clave

idempotencia

El agente corregido recibe el timeout y vuelve a llamar con refund:req_refund_001.

select * from refunds where attempt_id = A2 and operation_key = 'refund:req_refund_001';
-- encontrado, fingerprint igual → {ok: true, replayed: true, receipt_id: rf_9}
-- se inserta un evento 'tool.create_refund.replay'; el ledger no cambia
ResultadoUn reembolso, dos llamadas. Si el agente cambiara el importe con la misma clave, la restricción única y el fingerprint devuelven IDEMPOTENCY_CONFLICT sin tocar el ledger.

4. El worker se cae a mitad de un mundo

recuperación

El proceso muere tras el evento 3. El lease vence a los 60 segundos y pgmq vuelve a entregar el mensaje.

-- nuevo worker, bajo bloqueo del run:
update runs set lease_token = gen_random_uuid(), lease_until = now() + interval '60 s' where id = R and lease_until < now();
update world_attempts set status = 'aborted', ended_at = now() where id = A1 and status = 'running';
insert into world_attempts (world_id, attempt_number, state, ...) values (W, 2, fixture_con_mutaciones, ...);
update worlds set active_attempt_id = A2 where id = W;
ResultadoLos eventos del intento 1 se conservan con su cadena de hashes. El intento 2 arranca desde el fixture limpio. Si el worker viejo despierta y escribe, su lease_token ya no coincide y la función lanza LEASE_INVALID.

6. Un usuario intenta leer el run de otro

aislamiento

Con el ID de un run ajeno, prueba la API, la tabla y el canal Realtime.

ResultadoTres puertas, una sola regla: owner_id = auth.uid(). El 404 en lugar de 403 evita confirmar que el recurso existe.

7. Exportar y verificar un bundle

evidencia

El export incluye los eventos con sus hashes y el hash final de la cadena. Un verificador externo recorre la lista.

for e in bundle.events:
    expected = sha256(prev ‖ attempt_id ‖ seq ‖ canonical(e.payload))
    assert e.event_hash == expected      # cualquier alteración rompe aquí
    prev = e.event_hash
assert prev == bundle.chain_head
ResultadoLa evidencia se puede adjuntar a un ticket de cambio o a una auditoría y comprobarse sin acceso a la base. Los campos cifrados se exportan descifrados solo si quien exporta es el dueño, y la exportación queda en access_log.

8. Rotación de claves

cifrado

Dos rotaciones distintas, con costes muy distintos.

-- Rotar la KEK: solo se re-envuelven las DEK (una fila por propietario)
update core.data_keys set wrapped_dek = :nuevo_wrap, kek_id = 'kek-2026-11' where id = :key_id;

-- Rotar la DEK de un propietario: nueva clave activa; las filas viejas siguen legibles por su key_id
update core.data_keys set status = 'retired' where owner_id = :o and status = 'active';
insert into core.data_keys (owner_id, kek_id, wrapped_dek) values (:o, 'kek-2026-11', :wrap);
ResultadoNinguna rotación obliga a reescribir eventos. Un trabajo de fondo puede recifrar filas antiguas si una política lo exige.

9. Retención de 30 días para texto de modelo

minimización
select cron.schedule('purge-live-text', '15 3 * * *', $$
  set local premortem.retention = 'on';
  update public.events set payload_enc = null
   where payload_enc is not null and created_at < now() - interval '30 days';
$$);
ResultadoEl ledger, los hallazgos y los campos estructurados se conservan; el texto libre desaparece. La cadena de hashes se calculó sobre el texto cifrado, así que se guarda el hash del blob antes de anularlo para que el export siga verificable. El plazo debe validarse con el responsable del SGSI.

Cuando llegue el proyecto de Supabase

  1. 01
    Vincular y migrar

    supabase link y supabase db push desde el repositorio. Las migraciones crean los dos esquemas, las tablas, los triggers y las funciones. Nada se crea a mano en el panel.

  2. 02
    Extensiones

    pgcrypto para hashes, pgmq para la cola, pg_cron para retención, hstore para el trigger de inmutabilidad. Comprobar que pgmq funciona también en local antes de depender de él.

  3. 03
    Exposición de API

    En la configuración de la API dejar solo public como esquema expuesto. Verificar que core no responde ni con la clave de servicio desde el navegador.

  4. 04
    Rol del worker

    Crear premortem_worker con los grants anteriores. Su contraseña y la KEK van a las variables de entorno del worker y de la API, nunca al chat ni al repositorio. Si una credencial se pega por error en un canal, se rota de inmediato.

  5. 05
    Realtime privado

    Activar canales privados y aplicar la política sobre realtime.messages. Probar que un usuario ajeno no puede suscribirse.

  6. 06
    Copias y recuperación

    Si el plan lo permite, activar recuperación a un punto en el tiempo. Si no, respaldo diario programado. La evidencia exportada es la segunda copia.

  7. 07
    Semilla y prueba de aislamiento

    Ejecutar seed:demo, crear dos usuarios y correr la prueba de que uno no ve al otro antes de la primera demo.

Decisiones que quedan abiertas. Si cifrar también los payloads de los agentes de referencia (son sintéticos; la recomendación es no, por velocidad y simplicidad). El plazo de retención del texto de modelo. Y si la KEK pasa a Vault en la primera semana o se queda en variable de entorno hasta tener clientes externos. Ninguna obliga a cambiar el esquema.
